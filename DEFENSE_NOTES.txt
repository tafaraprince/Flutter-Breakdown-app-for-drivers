Breakdown Helper — Defense Notes

Elevator pitch
---------------
Breakdown Helper is a cross-platform Flutter app that helps drivers report vehicle breakdowns and quickly find nearby helpers (mechanics/tow operators). Users share location and a short description; the app returns sorted nearby helpers with distance, an approximate ETA and a rough cost estimate. The app is designed for demo and rapid extension to real backends.

Goals and success criteria
---------------------------
- Primary goal: enable a user to request nearby assistance quickly and securely.
- Secondary goals: polished UI (Rive animation and hero transitions), simple authentication, and resilient demo behavior when backend resources are missing.
- Demonstrable success: create a breakdown request, find nearby helpers, and initiate a phone call to a helper.

High-level architecture
------------------------
- Frontend: Flutter single codebase (mobile/web/desktop). UI screens handle user flows and display data.
- Services: small service layer (BreakdownService, DriversService, AuthService, LocationService) isolates API calls and platform-specific logic.
- State: Provider-based `SessionState` for authentication and current user session.
- Models: `BreakdownRequest` transports data between screens and to backend.

User flow / Data flow (story)
------------------------------
1. Splash screen -> Login/Signup (or guest).
2. User opens the Breakdown form: app obtains device location via `LocationService`.
3. User selects issue type and adds a description; app builds a `BreakdownRequest` (uuid, userId, lat/lon, timestamp) and calls `BreakdownService.createBreakdown()` to persist it.
4. If the backend is unavailable or a required table is missing, the app displays a SnackBar and proceeds in demo mode so the user can continue the flow.
5. App navigates to `NearbyHelpersScreen` passing the request; `DriversService.getNearbyDrivers()` returns candidates (demo or API), the app computes distances and ETA, sorts results, and displays driver cards.
6. User can press Call to open the device dialer (via `url_launcher`).

Key files and responsibilities
------------------------------
- lib/main.dart — app entrypoint, theme and routes.
- lib/models/breakdown_request.dart — the request model.
- lib/state/session_state.dart — manages authentication and session.
- lib/services/* — API/service wrappers (auth, breakdown, drivers, location).
- lib/ui/* — screens (splash, auth, breakdown form, nearby helpers) and UI components.
- assets/images/logo.png — app logo (hero image used across screens).
- pubspec.yaml — dependencies: flutter, provider, geolocator, supabase_flutter, url_launcher, rive, uuid.

Data contracts
---------------
BreakdownRequest:
- id: String (UUID)
- userId: String
- type: BreakdownType (enum)
- description: String
- latitude: double
- longitude: double
- createdAt: DateTime

Driver representation (used by DriversService):
- id, name, vehicle, phone, latitude, longitude
- derived/semi-random demo fields: rating, completedServices, yearsExperience, estimatedCost

Technical choices & rationale
------------------------------
- Flutter: single codebase for mobile, web and desktop — good for demos and a broad audience.
- Provider: minimal state management; easy to reason about for this scope.
- Supabase: authentication and database backend (open-source Firebase alternative). SDK makes auth and DB straightforward in Flutter.
- Geolocator: establishes device location for the core feature.
- Rive: lightweight vector animations for polish.

Privacy and security
---------------------
- Location: requested at the breakdown form, clearly described in the UI as used only for finding helpers. No background tracking is implemented.
- Network: Supabase SDK uses HTTPS.
- Fallback behavior: If the database/table is missing, the app falls back to a dev/demo flow and doesn't block the UX or leak data.

Testing & quality
------------------
- `flutter analyze` is used; current run reports only warnings/infos (deprecated usages and style lints), no compile-time errors.
- Minimal widget test exists (test/widget_test.dart) — good start for expanding coverage.
- Manual test checklist: auth flows (signup/login/guest), submit breakdown with location, view nearby helpers, call a helper.

Known limitations & technical debt
----------------------------------
- ETA and cost estimates are simplistic; production requires traffic data and live pricing.
- Drivers list is demonstrative — production needs proper geospatial queries (PostGIS or DB-side geolocation).
- Several analyzer infos flagged: many `.withOpacity()` uses (deprecation info), `use_build_context_synchronously` occurrences, and deprecated `value` on form fields — these are straightforward fixes.
- No real-time request lifecycle (accept/decline, tracking) or in-app chat yet.

Roadmap / next steps
---------------------
- Integrate a real drivers registry and backend geospatial search.
- Add request lifecycle and push notifications (helpers accept/decline requests).
- Add stronger unit and widget tests, CI for analysis and testing.
- Replace demo randomization with server-sourced helper metadata.

Likely defense questions and suggested answers
----------------------------------------------
Q: How is user location protected?
A: The app requests location only at request time, displays a privacy note, and does not track in the background. All network calls go over HTTPS via the SDK.

Q: How accurate are ETA/cost estimates?
A: They’re approximate for demo. Production would use traffic APIs and real helper-supplied prices.

Q: What does the fallback behavior do when DB/table is missing?
A: The app shows a SnackBar and continues locally so the user can see the flow — useful for demos and developer setups without DB initialized.

Q: Could drivers accept requests?
A: Not yet. Next step is a request lifecycle with accept/decline and real-time updates (Supabase Realtime or WebSockets).

Technical talking points to emphasize
------------------------------------
- Cross-platform Flutter advantage: one codebase for web, mobile and desktop.
- Clear separation of concerns: UI, services, state, models.
- Resilient UX: demo fallback and helpful error UI.
- Extensible architecture: service layer can be wired to real endpoints with minimal changes.
